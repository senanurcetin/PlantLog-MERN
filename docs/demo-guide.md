# PlantLog public demo

The public `/demo` route is an **entirely read-only** presentation of the industrial logbook. It uses static, fictional records bundled with the frontend. It does **not** call the API, issue JWTs, seed MongoDB, or connect to real industrial equipment.

## Quick review (no credentials, database, or backend)

```bash
cd frontend
npm ci
npm run test:demo
npm run build
npm run dev
```

**Live public demo:** https://plantlog-nexus-demo.vercel.app/demo (NEXUS 2.0 branding). Opening the project root also leads to `/demo` on this static, guest-only deployment.

Open `http://localhost:5173/demo` in local development mode. The browser route is also accessible from the login screen via **Explore demo**.

## Demonstration walk-through

1. In **Overview**, inspect totals calculated from the example asset and log records, alongside recent events.
2. In **Asset registry**, search for equipment by name, serial, category or location; filter by status.
3. Select **View logs** on a particular asset to see its associated records.
4. In **Maintenance log**, search for a title, description, status or asset; filter by event type and remove the per-asset filter.
5. In **Demo insights**, inspect type distribution, recorded intake by UTC day, and open incident/maintenance cases grouped by equipment. Selecting **View history** applies the existing asset log filter; it is a workload count, not a reliability score.
6. In **Scenario lab**, select an in-service fictional asset and advance one simulated incident through Report, Acknowledge, In progress and Resolve. Open **Demo insights** or the maintenance log to see its temporary effects. Choose **Reset simulation** to remove it.
7. Reload the page. No data can be saved, and the original fixture is restored.

## Static hosting

The Vercel project `plantlog-nexus-demo` uses `frontend/` as root and sets `VITE_PUBLIC_DEMO_ONLY=true` for production. In that build all other application paths redirect to `/demo` and links to login/register are replaced with source-code links, because **no backend is deployed**. The source repository is connected to Vercel on `main`.

Deploy **only** the `frontend/` directory to a static host if demonstrating `/demo` without the API. Use the root directory `frontend`, build command `npm ci && npm run build`, and output directory `dist`. For Vercel, the included `frontend/vercel.json` provides SPA rewrites for the known application routes. Other hosts need an equivalent `/demo` -> `index.html` fallback. Other authenticated application views will not be functional without their own backend.

**This route is a portfolio example, not a validated CMMS, safety system, digital twin or live telemetry source.**

The illustrative public logbook now includes a few **entirely fictional** status timelines (e.g., synthetic hydraulic service), viewable by expanding an activity item. Dates and actors are invented. The authenticated `/analytics` page is a separate backend-backed feature; the public demo does not simulate MTTR/MTBF or claim a real asset uptime measurement.

## Static analytics interpretation

The fourth public tab, **Demo insights**, derives all counts from the same
fictional `frontend/src/demo/fixture.json`. The eight UTC-date intake
buckets end at the fixture snapshot date and cover all sample records;
any record outside that window is counted explicitly. Open
incident/maintenance records exclude inspections and operations, which
are disclosed separately if unresolved.

**No** true failure probability, equipment uptime, downtime, MTTR, MTBF,
production throughput or safety conformance is inferred. The component
reuses the same equipment-to-log drill-down as the registry. Unit tests
in `frontend/tests/demo-insights.test.cjs` validate the cohort arithmetic,
date boundaries, empty data and missing-asset accounting.

## Scenario lab: educational interaction without productization

The fifth public tab adds **one temporary, fictional incident** to the
existing synthetic records. Visitors can advance an allowed four-stage
lifecycle, observe calculated summary changes, inspect its status history
in the existing logbook, and restore the baseline with Reset or reload.

- State exists only inside the React page instance; **no cookies, local or
  session storage, API requests, database writes, or downloads** are created.
- Visitors cannot assign an incident to an already decommissioned asset.
- The source fixture is never modified; stage transitions are deterministic
  and timestamped against the fictional snapshot, not the real clock.
- Simulator outputs are **not** a real maintenance dispatch workflow, alert,
  predicted failure, safety record, SLA, digital twin or production CMMS.
- Unit checks in `frontend/tests/demo-scenario.test.cjs` cover lifecycle
  ordering, resets, invalid transitions, recalculated analytics and absence
  of fixture mutation. The Chrome browser smoke walks the four stages and
  verifies the reset and zero-API behavior.

## Scientific data-quality checks

The public Demo Insights page now reports fixture data quality separately from
workload metrics, including dangling asset references, invalid UTC timestamps, timestamps
after the fixed observation date, duplicate asset/log IDs, missing log identities,
unknown record categories and invalid lifecycle statuses. An eligible record may have multiple exclusion findings: unique
eligible-row totals must not be inferred by summing issue counts. These checks
only demonstrate internal synthetic-data consistency; they do not establish
external predictive validity, actual industrial uptime, real-world causal
relationships or safety assurance.

## Inspectable scientific audit artifact

Every `npm run test:demo` executes a machine-verifiable fixture audit and
writes `frontend/test-artifacts/scientific-evidence.json`. The GitHub frontend
CI job uploads it as `plantlog-synthetic-science-evidence`, including the
input fixture SHA-256, eight quality gates and both five-case controlled
experiment families. Repeated runs of unchanged source inputs must produce
byte-identical JSON; see the [complete scientific protocol](eligibility-sensitivity-method.md).
Controlled added records have valid unique synthetic IDs, except the
intentionally broken asset-link example is explicitly ineligible.

## Independently verify an archived synthetic evidence report

The guest-only synthetic JSON report can also be verified **offline and
without CI**. First generate it using `npm run test:demo`, then run
`npm run evidence:verify` inside `frontend/`; alternatively pass the
path of an archived JSON report to
`node scripts/verify-scientific-evidence.cjs saved-report.json`.
The independent verifier enforces schema version 5, canonical JSON bytes,
a 1 MiB input limit and complete reconstruction from the local fixture
and checked-out source. It returns a nonzero exit code on altered or stale
evidence and never writes the inspected file. This is not a digital signature
or external event-provenance verification. Full methodology:
[offline evidence verification](offline-evidence-verification.md).

## Data-eligibility sensitivity laboratory

A separate interactive panel compares **raw descriptive** and **quality-eligible**
workload under five independently reconstructed datasets: original fixture,
missing equipment link, impossible UTC date, duplicated event ID, and several
errors on the same record. Every perturbation changes just **one existing**
fictional row; it never changes the source fixture or sends an API request.
Ambiguous duplicates cause **both** rows to fail, while overlapping quality
findings exclude their shared row only **once**.

The raw-versus-eligible difference is an arithmetic sensitivity check, not a
failure model, risk probability, causal estimate or real plant statistic.
See the [protocol, denominator and limitations](eligibility-sensitivity-method.md).

## Lifecycle fault-injection laboratory

The guest Demo Insights page now offers an **independent, eleven-case
fictional status-history experiment**. Select a deliberately corrupted version
of one documented maintenance chain to observe nine diagnostic categories,
including missing histories versus invalid timelines and overlapping defects.
The experiment **does not** alter the original records or change the eight
basic eligibility rules. A separate exhaustive model check enumerates
19,531 fictional action-attempt prefixes and confirms rejection, reset and
in-memory timeline invariants; it does not exercise the production system.
See [model and fault-injection methodology](lifecycle-traceability.md).

## Combined review facets

The workbench now also filters **simultaneously** by its exclusive
documentary review group, original history classification, and observed
diagnostic code. This distinguishes a basic-data exclusion from a timeline
contradiction even if both occur in one fictional row. Issue counts overlap,
so the number of filtered rows is computed from unique positions, not from
adding diagnostic frequencies. Filters are local, reset upon changing the
example population, and do not save an investigation outcome.

## Failure isolation for lazy experiments (development branch)

A `SyntheticLabErrorBoundary` contains dynamic import or panel-render
errors to the **selected research panel**. The surrounding synthetic
maintenance workload, data-quality checks, navigation and six lab selectors
remain available. The fallback gives a short accessible error announcement
without exposing stack traces, source identifiers or simulated hardware
conclusions. Users may switch to the default controlled-comparisons panel,
or reload the entire guest demo to retry a failed import.

JavaScript caches a failed dynamic module import during the page session,
so simply rerendering the same panel is **not** promised as a retry.
The reload action explicitly states that temporary fictional cases and
experiment selections are cleared. Neither recovery action writes
to the database or sends error telemetry.

## Verified on-demand JavaScript loading (development branch)

The six laboratories now use React `lazy()` and Vite dynamic imports,
so choosing an experiment downloads its dedicated code chunk only when needed.
Selecting **Demo insights** initially requests only the default controlled
comparison code; the other five experimental interfaces and their specific
dependencies are not eagerly included in that screen's initial bundle.
Already loaded modules are cached by the browser. A bounded loading message
is shown while a requested chunk resolves.

The production-bundle regression asserts six named deferred chunks and
a reduced initial JavaScript budget. Local Playwright network interception
independently asserts that opening the homepage loads **no** scientific
laboratory chunks, selecting insights loads **only** the comparison chunk,
and selecting all six subsequently requests each experiment once.
These tests are local-only, do not contact a backend, and do not constitute
measurements of the published Vercel deployment.

The synthetic evidence computations, report schema v5, source fixture
and no-industrial-connectivity claims are unchanged.

## On-demand research laboratory navigation (development branch)

The Demo Insights screen now separates its fixed summary from **six
individually selectable scientific panels**: controlled comparisons,
eligibility sensitivity, lifecycle fault injection, UTC boundaries,
evidence matrix and document review. Only **one experimental panel** is
mounted and calculated at a time; the overview's quality, lifecycle and
workload summaries always remain present.

The selector is a keyboard-operated button group with explicit
`aria-pressed` state, rather than an unimplemented tab-widget keyboard
pattern. Switching panels discards only that panel's transient selection,
never edits records, and never caches, stores or uploads review choices.
Returning from another demonstration section or reloading restores
controlled comparisons as the initial panel. This is **progressive UI
disclosure**, not fewer quality checks or a change to scientific evidence
criteria.

and are **not** evidence that this unmerged branch is deployed. The new

## Cross-axis evidence and eligibility explorer

The Demo Insights screen additionally exposes a **2 × 3 synthetic evidence

## UTC chronology boundary lab

The synthetic insights panel includes **12 fixed UTC boundary experiments**
for day-end millisecond equality, leap days, year rollover, timezone
format enforcement, reversed transitions and missing history. Basic
log eligibility is distinguished from the validity of a status-event
timeline; a case can be an eligible descriptive log but have an invalid

result without modifying any fixture record or calling an API.

## Controlled synthetic comparison examples

The live Demo Insights section also compares five deterministic
counterfactual fixtures: no change, one new open incident, one new open
maintenance record, one resolved incident and one unlinked incident.
Every row starts from the **same baseline** and adds at most one fictional
record. The table exposes absolute counts and differences for total logs,
open incident/maintenance cases, affected equipment and unlinked cases.

These outcomes are bookkeeping identities, **not** evidence for causal
relationships, reliability engineering coefficients, forecasting or
mechanical failure severity. The fixture remains unchanged.

## Additional data-quality and accessibility safeguards

The data-quality panel excludes **all rows carrying repeated log identifiers**
or pointing at ambiguous duplicate equipment identifiers from its eligible-row
numerator. It also excludes missing/blank log IDs, unsupported event categories
and malformed dates. It does not sum overlapping errors to invent a count of
unique invalid rows. The fixture timestamp contract requires real calendar
instants encoded with an explicit UTC `Z` designator, with optional
millisecond precision (not local-time strings or numeric timezone offsets).
This strict UTC contract is a reproducibility policy for the demo, not an
assertion that all other ISO 8601 timestamps are universally invalid.

**Interpretation:** quality eligibility and workload charts are intentionally
separate: the quality panel reports excluded records, while the descriptive
charts count the raw fictional fixture. When checking a modified fixture,
inspect the quality panel before treating raw chart counts as trustworthy.

The NEXUS demo provides a visible-on-focus **Skip to demonstration content**
link and honors the operating system's reduced-motion preference. The
browser smoke test checks keyboard access to the main content.
Automated checks do not constitute WCAG certification.
